# Timing, fairness and ranking in BringMe!

**Short version:** BringMe! measures how long each player took with millisecond *resolution*, but it does **not** claim millisecond *accuracy* or perfect fairness across different phones and networks. Times are good enough to rank most rounds; results that are very close are flagged as **"too close to call"** and the Game Master decides from the photos. The client's measurement is a *claim* that the server cross-checks, never an authoritative anti-cheat guarantee.

## 1. What is recorded

For every accepted photo the database stores three independent pieces of evidence, all relative to the round's **official start** (`game_rounds.opened_at`, generated by the database):

| Field | Source | Meaning |
|---|---|---|
| `claimed_elapsed_ms` | the player's browser | Elapsed time at the **moment of the tap** (not when the upload finished). A *claim*. |
| `server_elapsed_ms` | the database clock | When the **server first heard** about the tap (`intent_at − opened_at`) = tap + one network hop. |
| `received_elapsed_ms` | the database clock | When the upload was confirmed. Always ≥ the previous one. Used for upload-latency forensics only. |
| `client_meta` | the browser (sanitised) | Clock-sync quality (`syncRttMs`, `syncAgeMs`, `syncUncertaintyMs`), camera facing, frame size, upload time, attempts. Whitelisted and clamped server-side. |
| `timing_flags`, `timing_status` | the database | Result of the cross-checks below. |
| `rank_ms` | the database | The single number used for ranking (§3). |

## 2. How the client measures

1. **Official start** is a server timestamp (`opened_at`). The countdown and the reveal of the item both follow server timestamps, so every device agrees on *when* the round starts, up to the clock estimate below.
2. **Clock offset.** Every snapshot fetch brackets a request with `performance.now()` (monotonic) and receives the database clock reading. The server time is assumed to be the midpoint of the request, so the error is at most **RTT/2** (more if the network path is asymmetric). We keep the lowest-RTT recent sample (`lib/game/clock.ts`) and at countdown start we take a short burst of extra samples.
3. **Elapsed time at the tap** = `serverNow(performance.now() at tap) − opened_at`. `serverNow` projects the chosen sample forward using only monotonic deltas, so changing the phone's wall clock mid-game cannot affect it.
4. The tap is captured on **pointer-down** (not after the click delay) and the video frame is grabbed synchronously in the same handler. `begin` is sent immediately, *before* compression and upload, so network speed cannot change the measured time.

## 3. Ranking policy

```
rank_ms = claimed_elapsed_ms           if the claim is consistent with the server's evidence
        = server_elapsed_ms            if it is flagged (conservative: includes the player's own network delay)
order   = rank_ms  ASC,
          server_elapsed_ms ASC,       (whose tap the server heard first)
          submitted_at ASC, id         (arrival order, to be deterministic)
```

**Consistency checks** (`complete_submission`, hard flags ⇒ `timing_status = 'flagged'`):

| Flag | Condition | Why |
|---|---|---|
| `elapsed_negative` | claim < −250 ms | claims to be before the official start |
| `intent_before_capture` | server heard the tap > 250 ms *before* the claimed capture instant | impossible: the claim says "later" than something already observed |
| `intent_lag_high` | server heard the tap > **1 s** after the claimed instant | one network hop is normally < 150 ms; > 1 s is a very slow network **or an inflated lead** |
| `elapsed_exceeds_limit` | claim > time limit + 2 s | outside the round |

Soft flags (recorded, shown to the host, do **not** change ranking): `intent_lag_elevated` (> 400 ms), `sync_unknown`, `sync_rtt_high` (> 1.5 s), `sync_stale` (> 2 min since the last clock sample), `upload_slow` (> 20 s).

**Maximum undetected advantage.** A modified client can claim a time up to **1 s earlier** than the server observed without being flagged. That bound is a deliberate trade-off: tightening it penalises honest players on bad mobile networks (they would fall back to server time and lose their own latency), loosening it makes inflation easier. Because the bound is large compared with the near-tie window, treat the ranking as a **strong suggestion, not proof**.

### Review, eligibility and who actually wins (Phase 9)

Timing only *orders* the photos; it never decides alone. A submission is **eligible** to win only if the Game Master has **approved** it (`submissions.status = 'approved'`) and the player is still in the game.

```
winner = first row of:  approved submissions ORDER BY rank_ms, server_elapsed_ms, submitted_at, id
```

* The **server computes the winner**. The host's "Declare winner" sends the winner they *saw* as a confirmation; if the ranking changed meanwhile (a late photo, another decision) the server answers `winner_mismatch` and announces nothing.
* **Disqualified** and **pending** photos never win. A timing-flagged photo stays eligible but ranks by the server-observed time.
* **No approved photo ⇒ no winner.** The host can announce "no winner", and that is final too.
* The announcement is **write-once**: `winner_confirmed_at` is set once, review decisions lock, and a second announcement is rejected (`invalid_transition`).

### Near ties

Two neighbouring results whose `rank_ms` differ by **less than 150 ms** (`NEAR_TIE_MS`, `round_ranking(p_near_ms)`) are marked `near_tie`, and the host panel shows **"too close to call"**. 150 ms is a rounded estimate of the combined uncertainty of two devices: clock-sync error (up to RTT/2 each, typically 10–50 ms on good connections, more on cellular), touch-to-JavaScript latency (10–50 ms and device-dependent) and camera preview latency (30–150 ms). The Game Master then:

1. looks at the photos (they are the real judge of *"did they bring the item?"*),
2. approves/disqualifies, then confirms the announced winner (the confirmation dialog repeats the close finish and any photos still unreviewed),
3. disqualify the photo that does not show the item (then it is no longer a contender and the next approved photo leads). The review screen shows the two close photos side by side;
4. if both are valid, the established order decides (below). It is deterministic, not "more accurate".

Tie-break order used when `rank_ms` is equal or both valid: the server-observed order (`server_elapsed_ms`, then arrival order) is already used for the display order. It is deterministic, not "more accurate".

## 4. What we do NOT guarantee

- **No cross-device millisecond fairness.** Different phones have different touch latency, sampling rates, camera pipelines and browsers (some reduce `performance.now()` precision for privacy, e.g. Firefox with resist-fingerprinting, Safari rounding).
- **The photo is not the tap.** `drawImage(video)` returns the newest decoded frame, which already lags the real world by the camera pipeline delay.
- **Clock sync is an estimate.** Error ≤ RTT/2 for symmetric paths, larger for asymmetric ones. We record how good the estimate was so the host can see it.
- **A determined cheater can still win small amounts.** The client code can be modified to send any claim and any image. We bound the *timing* gain (1 s), require the photo to be uploaded within **45 s of the tap** (so one cannot "tap early, find the item later"), make a *new* capture reset its timing, keep one submission per player per round, and show the photo to a human judge. We do not attempt device attestation.
- **Gallery uploads** are not offered (live `getUserMedia` stream + canvas capture only, no file input), but a modified client could still upload an old image. The server verifies type/size/JPEG signature, not provenance.
- **Retention:** the photo-retention setting is stored but the cleanup job is not built yet.

## 5. Tunables (all in one place)

| Constant | Value | Where |
|---|---|---|
| Near-tie window | 150 ms | `round_ranking(p_near_ms)`, `lib/game/timing.ts` |
| Upload window after the tap | 45 s (trigger backstop 50 s) | `begin_submission`, `complete_submission` |
| Lead tolerance (hard / soft) | 1 s / 400 ms | `complete_submission` |
| "Server heard it before it happened" tolerance | 250 ms | `complete_submission` |
| Clock samples kept / considered fresh | 16 / 2 min | `lib/game/clock.ts` |
| Photo budget | ≤ 1.6 k px long edge, JPEG ≤ 1.5 MB (quality ladder 0.82 → 0.45) | `lib/game/camera.ts` |

If you change a threshold, change it in SQL **and** `TIMING.md`, then update `tests/db/submissions.test.ts`.
